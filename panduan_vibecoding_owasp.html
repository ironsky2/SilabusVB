🛡️ PANDUAN KEAMANAN APLIKASI WEB & AI CODING

OWASP (Open Web Application Security Project) Top 10 untuk Vibe Coder Pemula:
Cara Menjaga Aplikasi AI Tetap Aman dari Serangan

Panduan praktis bagi pemula non-IT yang belajar membuat aplikasi dengan bantuan AI (Vibe Coding). Tujuannya bukan untuk mencetak pakar keamanan siber, melainkan membuat Anda tahu apa yang harus diminta ke AI agar kode yang dihasilkan tidak hanya berfungsi, tetapi juga kokoh dan tidak mudah dibobol.

🛡️ Standar: OWASP Top 10:2021
🤖 Metode: Vibe Coding (Prompt-Driven Security)
🎯 Target: Pemula Tanpa Latar Belakang IT
📋 Format: Teori, Risiko Kode AI & Master Prompt Siap Pakai
A01: Access Control A02: Kriptografi A03: Injection A04: Insecure Design A05: Misconfiguration A06: Komponen Usang A07: Autentikasi A08: Integritas Data A09: Logging & Monitor A10: SSRF 🧪 Lab Studi Kasus (MyOrder) ⚡ Universal Prompt 💡 Tips Keamanan

🏛️ Mental Model: Kenapa AI Sering Menulis Kode yang Rentan?

AI selalu memprioritaskan kode yang paling singkat dan "langsung kelihatan jalan". AI tidak akan menambahkan pengecekan kepemilikan data, hashing password, atau parameter query KECUALI Anda memintanya secara eksplisit!

[ PROMPT POLOS: "Buatkan fitur login" ] ---> [ AI Menulis Jalan Pintas ] ---> [ Password Plaintext / Rawan SQLi ] ❌ [ PROMPT OWASP: + Syarat bcrypt & SQLi ] ---> [ AI Menulis Kode Aman ] ---> [ Terproteksi Standar Industri ] ✅
💡 Cara Pakai Modul Ini: Setiap bab risiko di bawah dilengkapi 2 jenis Master Prompt: (1) Prompt Membangun Fitur Baru dan (2) Prompt Mengaudit / Mengecek Kode yang Sudah Ada. Salin dan gunakan langsung pada AI coding assistant Anda!
A01

Broken Access Control (Kontrol Akses yang Rusak)

Kategori risiko #1 OWASP: Siapa yang boleh melihat, mengedit, atau menghapus data.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Ini soal otorisasi data. Contoh gagal: Pengguna A bisa melihat struk pesanan Pengguna B hanya dengan mengganti angka di URL dari id=101 menjadi id=102. Aplikasi hanya mengecek *"apakah ID 102 ada di database?"*, bukan *"apakah ID 102 milik user yang sedang login?"*.

⚠️ Kenapa Bahaya Buat Vibe Coder?
AI sangat sering membuat endpoint seperti GET /api/order/:id yang berfungsi sempurna saat Anda uji sendiri dengan 1 akun. Namun celah bocornya data baru ketahuan saat orang lain iseng mengganti angka ID di URL browser.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A01.1: MEMBANGUN FITUR DENGAN AKSES AMAN 
Buatkan endpoint untuk melihat detail pesanan berdasarkan order_id.
Syarat wajib keamanan (OWASP A01):
1. Ambil identitas user yang sedang login dari session/token aman, JANGAN dari parameter yang dikirim client.
2. Sebelum mengembalikan data, cek apakah order_id tersebut memang milik user_id yang sedang login.
3. Kalau bukan miliknya, kembalikan response error 403 Forbidden, bukan data milik orang lain.
4. Tulis juga 1 contoh test case yang mencoba mengakses order milik user lain untuk membuktikan proteksinya berjalan.
🔍 PROMPT A01.2: MENGECEK KODE DARI BROKEN ACCESS CONTROL 
Ini kode endpoint saya:
[TEMPEL KODE ANDA DI SINI]

Tolong cek khusus dari sisi Broken Access Control (OWASP A01):
- Apakah ada endpoint yang mengambil data berdasarkan ID dari user tanpa memverifikasi kepemilikan data tersebut?
- Apakah ada fitur admin yang bisa diakses user biasa jika dia mengetahui URL-nya?
Jelaskan tiap temuan dengan bahasa sederhana, lalu berikan kode perbaikannya.
✅ Proteksi yang Benar Setiap query database memuat klausa kepemilikan: WHERE order_id = $1 AND user_id = $current_user.
⚠️ Kesalahan Fatal Mempercayai user_id yang dikirim langsung dari form/URL tanpa mencocokkannya dengan session login.
A02

Cryptographic Failures (Kegagalan Kriptografi)

Melindungi data sensitif (password, token, data pribadi) dengan enkripsi dan hashing yang tepat.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Terjadi saat data sensitif (password, nomor kartu, NIK) disimpan dalam bentuk teks polos (plaintext), dikirim tanpa protokol HTTPS, atau di-hash menggunakan algoritma usang yang mudah dipecahkan (seperti MD5 atau SHA1).

⚠️ Kenapa Bahaya Buat Vibe Coder?
Saat Anda meminta AI "buatkan sistem login", AI terkadang menyimpan password langsung ke database tanpa di-hash, atau memakai MD5. Tidak ada error sama sekali pada website Anda — hingga database Anda bocor ke publik.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A02.1: SISTEM REGISTRASI & HASHING AMAN 
Buatkan sistem registrasi dan login user.
Syarat wajib keamanan (OWASP A02):
1. JANGAN PERNAH simpan password dalam bentuk plaintext.
2. Gunakan algoritma hashing password standar industri saat ini (misalnya bcrypt atau argon2), bukan MD5 atau SHA1.
3. Data sensitif lain (contoh: token reset password) harus dibuat secara acak dan aman (cryptographically secure random).
4. Jangan pernah menampilkan atau mengirimkan password asli lewat email atau log aplikasi.
Jelaskan juga di komentar kode alasan pemilihan algoritma tersebut.
🔍 PROMPT A02.2: AUDIT KRIPTOGRAFI PADA KODE 
Cek kode ini dari sisi Cryptographic Failures (OWASP A02):
[TEMPEL KODE ANDA DI SINI]

- Apakah ada password atau data sensitif yang disimpan tanpa hashing/enkripsi yang layak?
- Apakah ada data sensitif yang dikirim lewat HTTP biasa atau tercatat di console.log?
Berikan daftar temuan dan cara perbaikannya, urutkan dari yang paling berbahaya.
✅ Proteksi yang Benar Password di-hash dengan bcrypt.hash(password, 10) dan kunci rahasia disimpan di Environment Variables.
⚠️ Kesalahan Fatal Menyimpan password asli dalam kolom database atau menggunakan enkripsi dua arah yang bisa didekripsi kembali.
A03

Injection (SQL Injection & Command Injection)

Mencegah input berbahaya dari user disalahartikan sebagai perintah program.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Terjadi jika input dari user dipercaya begitu saja dan digabung langsung ke perintah database. Contoh legendaris: penyerang mengetik ' OR '1'='1 di kolom login dan berhasil masuk tanpa mengetahui password asli.

⚠️ Kenapa Bahaya Buat Vibe Coder?
AI sering membuat query dengan cara menggabungkan teks (string concatenation: "SELECT * WHERE user = '" + input + "'") karena itu cara tercepat. Tanpa instruksi eksplisit untuk memakai parameterized query, aplikasi Anda sangat rentan dieksploitasi.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A03.1: QUERY DATABASE ANTI-INJECTION 
Buatkan fitur pencarian produk berdasarkan nama yang diketik user.
Syarat wajib keamanan (OWASP A03):
1. Gunakan parameterized query / prepared statements untuk semua query database. JANGAN PERNAH gabungkan input user langsung ke string SQL.
2. Validasi tipe data dan panjang karakter input sebelum diproses.
3. Tunjukkan perbandingan kode versi SALAH (rawan SQL Injection) dan versi BENAR agar saya paham perbedaannya.
🔍 PROMPT A03.2: SCANNING INJECTION PADA KODE 
Cek kode ini khusus untuk kerentanan Injection (OWASP A03):
[TEMPEL KODE ANDA DI SINI]

- Cari semua baris yang menggabungkan input user langsung ke query database, command shell, atau innerHTML tanpa sanitasi.
- Untuk tiap temuan, berikan contoh input jahat yang bisa dipakai menyerang serta kode perbaikannya.
✅ Proteksi yang Benar Menggunakan placeholder: db.query('SELECT * FROM users WHERE email = $1', [userEmail]).
⚠️ Kesalahan Fatal Menulis template literal: `SELECT * FROM users WHERE email = '${userEmail}'`.
A04

Insecure Design (Desain Sistem yang Tidak Aman)

Mencegah cacat logika pada alur bisnis aplikasi sebelum baris kode ditulis.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Berbeda dari bug pemrograman, ini adalah fitur yang dari awal *salah dirancang*. Contoh: Fitur reset password via OTP 6 digit, namun tidak membatasi berapa kali orang boleh menebak angka OTP tersebut (tidak ada batas percobaan / rate limit).

⚠️ Kenapa Bahaya Buat Vibe Coder?
Vibe coder cenderung fokus pada *"apakah fiturnya berjalan"*, bukan *"bagaimana jika orang jahat menyalahgunakan alur ini"*. AI tidak akan memikirkan skenario penyalahgunaan kecuali Anda memintanya melakukan threat modeling.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A04.1: DESAIN FITUR AMAN & THREAT MODELING 
Saya ingin membuat fitur: "Reset password lewat kode OTP 6 digit yang dikirim ke email".
Sebelum menulis kode, tolong lakukan analisa terlebih dahulu:
1. Apa saja skenario penyalahgunaan yang mungkin terjadi (contoh: bot menebak semua kombinasi OTP)?
2. Bagaimana desain arsitektur yang aman untuk mencegahnya (rate limiting, masa kedaluwarsa OTP 5 menit, batas percobaan maksimal 3x)?
Setelah desain disepakati, baru buatkan kodenya berdasarkan arsitektur aman tersebut.
🔍 PROMPT A04.2: REVIEW ALUR LOGIKA BISNIS 
Ini alur fitur [NAMA FITUR] pada aplikasi saya:
[JELASKAN ALUR / TEMPEL KODE]

Sebagai reviewer keamanan, coba pikirkan skenario penyerangan: Skenario penyalahgunaan apa saja yang bisa terjadi pada alur ini yang belum dicegah oleh desainnya? Berikan rekomendasi perbaikan desain.
✅ Proteksi yang Benar OTP kedaluwarsa dalam 5 menit, batas salah maksimal 3 kali sebelum akun dibekukan sementara.
⚠️ Kesalahan Fatal Membuat OTP yang berlaku selamanya tanpa batas percobaan tebakan.
A05

Security Misconfiguration (Salah Konfigurasi Server & App)

Menutup celah akibat pengaturan bawaan yang terlalu longgar saat naik ke produksi.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Aplikasi rentan bukan karena kode error, tetapi karena pengaturannya teledor: Mode debug masih menyala di production, pesan error membocorkan struktur tabel database, atau CORS mengizinkan semua website (*).

⚠️ Kenapa Bahaya Buat Vibe Coder?
Boilerplate atau kode dari AI biasanya dibuat untuk kenyamanan lokal (DEBUG=True, CORS=*). Pengaturan ini sering terlupakan saat aplikasi di-deploy ke Vercel atau hosting publik.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A05.1: CHECKLIST HARDENING DEPLOY PRODUCTION 
Saya ingin men-deploy aplikasi [Express / Next.js / Supabase / dll] ke production.
Buatkan checklist konfigurasi keamanan sebelum go-live:
1. Pastikan mode debug / stack trace error mati total di production.
2. Konfigurasi CORS agar hanya mengizinkan domain frontend resmi saya, bukan '*'.
3. Pasang HTTP Security Headers standar (Content-Security-Policy, X-Frame-Options, HSTS).
4. Pastikan tidak ada halaman admin default yang terbuka tanpa password.
Setelah itu, audit file konfigurasi saya ini: [TEMPEL CONFIG / .ENV CONTOH]
🔍 PROMPT A05.2: AUDIT PENGATURAN & ENV 
Cek project ini dari sisi Security Misconfiguration (OWASP A05):
[TEMPEL FILE CONFIG / SETTINGS]

Cari pengaturan yang aman untuk development laptop tetapi berbahaya jika dipakai di internet publik (production), dan jelaskan resiko masing-masing.
✅ Proteksi yang Benar Pesan error ke pengguna hanya berupa: "Terjadi kendala teknis. Kode referensi: #123" tanpa detail database.
⚠️ Kesalahan Fatal Menampilkan seluruh pesan error database SQL beserta baris kodenya di layar pengguna umum.
A06

Vulnerable and Outdated Components (Komponen Usang & Rentan)

Menghindari penggunaan paket library pihak ketiga yang memiliki celah keamanan publik.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Website modern dibangun menggunakan puluhan package (npm, pip). Jika salah satu library memiliki celah keamanan yang tercatat publik (CVE) dan tidak diperbarui, penyerang bisa meretas aplikasi Anda dengan mudah.

⚠️ Kenapa Bahaya Buat Vibe Coder?
Vibe coder sering menjalankan npm install [nama-paket] yang disarankan AI tanpa memeriksa apakah library tersebut masih aktif dirawat atau sudah ditinggalkan pembuatnya sejak 5 tahun lalu.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A06.1: PEMILIHAN LIBRARY YANG AMAN 
Saya ingin menambahkan fitur upload dan kompresi gambar di website saya.
Sebelum merekomendasikan library:
1. Sarankan hanya library yang populer, teruji, dan aktif di-maintain dalam 6 bulan terakhir.
2. Jelaskan cara saya mengecek reputasi dan riwayat keamanan (vulnerability) library tersebut sebelum saya pasang.
🔍 PROMPT A06.2: AUDIT DEPENDENCY PACKAGE 
Ini isi file package.json / requirements.txt saya:
[TEMPEL ISI FILE DEPENDENCY]

Tolong:
1. Berikan perintah terminal untuk menjalankan audit keamanan otomatis pada stack saya (misal: npm audit).
2. Jelaskan langkah yang harus saya lakukan jika audit menemukan celah berbahaya.
✅ Proteksi yang Benar Menjalankan npm audit secara berkala dan memperbarui dependensi ke versi stabil terbaru.
⚠️ Kesalahan Fatal Membiarkan paket versi lama yang sudah terbukti memiliki celah zero-day tanpa pernah di-update.
A07

Identification and Authentication Failures (Kegagalan Autentikasi)

Mencegah serangan brute force password dan kebocoran sesi pengguna.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Proses login yang lemah membiarkan robot penyerang mencoba jutaan password tanpa dibatasi (brute force), token login tidak pernah kedaluwarsa, atau sistem memberitahu secara gamblang bahwa *"Email ini belum terdaftar"* (user enumeration).

⚠️ Kenapa Bahaya Buat Vibe Coder?
Sistem login dasar dari AI biasanya hanya mengecek if (password == cocok) tanpa mekanisme keamanan seperti rate limiter percobaan login atau penghancuran sesi saat logout.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A07.1: SISTEM LOGIN DENGAN RATE LIMITER 
Buatkan sistem login yang aman.
Syarat wajib keamanan (OWASP A07):
1. Batasi percobaan login yang gagal (maksimal 5 kali dalam 15 menit per IP/akun, lalu kunci sementara).
2. Session / JWT token wajib memiliki masa berlaku (expiry time).
3. Hancurkan session / revoke token secara total saat user menekan tombol Logout atau ganti password.
4. Gunakan pesan error umum: "Email atau password salah" (jangan beri tahu apakah email terdaftar atau tidak).
🔍 PROMPT A07.2: AUDIT SESI & ALUR LOGIN 
Cek alur login dan session pada kode ini (OWASP A07):
[TEMPEL KODE ANDA DI SINI]

- Apakah ada rate limiting untuk mencegah serangan tebak password otomatis?
- Apakah session bisa kedaluwarsa secara otomatis?
- Apakah pesan error membocorkan keberadaan akun pengguna?
✅ Proteksi yang Benar Pesan error generik dan token sesi disimpan di cookie dengan flag HttpOnly dan Secure.
⚠️ Kesalahan Fatal Menyimpan token autentikasi di localStorage yang mudah dicuri oleh serangan XSS JavaScript.
A08

Software and Data Integrity Failures (Kegagalan Integritas Software & Data)

Memastikan kode, update, dan data dari luar telah terverifikasi keasliannya.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Mempercayai kode eksternal, auto-update, atau plugin tanpa mengecek integritasnya (checksum/digital signature). Penyerang bisa menyisipkan kode jahat di tengah transmisi data (Man-in-the-Middle).

⚠️ Kenapa Bahaya Buat Vibe Coder?
Sangat relevan saat Anda memakai fitur auto-update, CI/CD pipeline otomatis di GitHub Actions, atau mengunduh file konfigurasi dinamis dari server luar.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A08.1: UNDUH & VERIFIKASI DATA EKSTERNAL 
Saya ingin membuat fitur di aplikasi yang mengunduh file konfigurasi/data dari server eksternal secara otomatis.
Sebelum menulis kode:
1. Jelaskan bagaimana cara memverifikasi keaslian file tersebut (misalnya pencocokan Checksum SHA-256 / Signature) sebelum dieksekusi oleh aplikasi.
2. Tuliskan kode lengkap yang menolak menjalankan file jika checksum tidak cocok.
🔍 PROMPT A08.2: AUDIT PIPELINE & INTEGRITAS KODE 
Ini alur proses CI/CD dan deployment saya:
[TEMPEL FILE WORKFLOW / CONFIG]

Apakah ada tahapan yang mempercayai kode dari luar tanpa verifikasi signature atau sumber yang terpercaya? Berikan rekomendasi pengamanannya.
✅ Proteksi yang Benar Memeriksa hash SHA-256 file sebelum membuka atau menjalankan isinya di server.
⚠️ Kesalahan Fatal Menjalankan perintah eval() langsung dari teks yang diunduh via URL publik.
A09

Security Logging and Monitoring Failures (Kegagalan Pencatatan Log)

Mencatat jejak aktivitas mencurigakan agar serangan bisa dideteksi sebelum terlambat.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: Jika aplikasi diserang tetapi tidak ada catatan (log) tentang siapa yang mencoba login ratusan kali, dari mana IP-nya, dan kapan kejadiannya, Anda tidak akan pernah tahu bahwa aplikasi Anda sedang dalam bahaya.

⚠️ Kenapa Bahaya Buat Vibe Coder?
Vibe coder biasanya tidak terpikir membuat logging karena logging "tidak terlihat di antarmuka website". Padahal tanpa log yang rapi, Anda baru sadar terjadi peretasan setelah data pelanggan hilang.

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A09.1: IMPLEMENTASI LOG KEAMANAN DASAR 
Tambahkan sistem logging keamanan dasar ke aplikasi saya.
Syarat wajib keamanan (OWASP A09):
1. Catat setiap percobaan login (sukses maupun gagal) beserta timestamp waktu dan IP address (TANPA mencatat password).
2. Catat aktivitas penting seperti perubahan role user, ganti password, dan transaksi pembayaran.
3. JANGAN PERNAH mencatat password, token rahasia, atau nomor kartu di log.
4. Jelaskan cara memantau log ini untuk mendeteksi anomali (misal: 10 login gagal berturut-turut).
🔍 PROMPT A09.2: AUDIT KELAYAKAN LOGGING 
Cek kode aplikasi saya dari sisi Logging & Monitoring (OWASP A09):
[TEMPEL KODE ANDA DI SINI]

- Aktivitas sensitif apa saja yang belum tercatat di log?
- Apakah ada data pribadi atau password yang tidak sengaja tercetak di dalam log?
✅ Proteksi yang Benar Mencatat aktivitas penting dengan sensor otomatis terhadap kata sandi dan token.
⚠️ Kesalahan Fatal Mencetak seluruh object request console.log(req.body) yang berisi password asli user ke log server.
A10

Server-Side Request Forgery / SSRF

Mencegah server Anda diperalat penyerang untuk mengakses data rahasia internal.

Part A · Teori & Mengapa Bahaya Buat Vibe Coder

Teori: SSRF terjadi jika aplikasi bisa disuruh melakukan fetch URL sembarangan. Contoh: Fitur *"masukkan URL gambar profil"*, lalu penyerang memasukkan alamat http://localhost:8080/admin-database sehingga server membaca datanya sendiri dan membocorkannya.

⚠️ Kenapa Bahaya Buat Vibe Coder?
Fitur seperti "import data dari link", "preview link website", atau "webhook URL" sangat sering diminta ke AI, dan AI biasanya membuatnya tanpa menyaring domain (tanpa whitelist domain).

Part B · Master Prompts AI Siap Pakai

🛡️ PROMPT A10.1: FITUR FETCH URL DENGAN WHITELIST AMAN 
Buatkan fitur: "Mengambil gambar profil dari URL yang dimasukkan user".
Syarat wajib keamanan (OWASP A10):
1. Buat whitelist protokol (hanya https://) dan blokir total akses ke alamat jaringan privat/internal (seperti localhost, 127.0.0.1, 10.x.x.x, 192.168.x.x).
2. Validasi ini WAJIB dilakukan di sisi Backend/Server, bukan hanya di frontend.
3. Jelaskan secara singkat skenario serangan SSRF yang dicegah oleh kode ini.
🔍 PROMPT A10.2: DETEKSI CELAH SSRF 
Cek kode ini dari sisi risiko Server-Side Request Forgery (OWASP A10):
[TEMPEL KODE ANDA DI SINI]

Cari semua bagian di mana server melakukan HTTP request (fetch, axios, curl) ke URL yang berasal dari inputan pengguna. Apakah ada mekanisme whitelist?
✅ Proteksi yang Benar Memblokir semua IP internal / loopback sebelum server mengirimkan permintaan jaringan.
⚠️ Kesalahan Fatal Membiarkan fungsi fetch(userUrl) berjalan bebas tanpa memverifikasi domain tujuan.
🧪 LAB

Laboratorium Praktikum: Studi Kasus Aplikasi "MyOrder" (Toko Online Mini)

Simulasi 4 Fase pengujian penetrasi (Ethical Hacking) dan hardening kode aplikasi nyata menggunakan AI.

Untuk memahami bagaimana 10 risiko OWASP terjadi di dunia nyata, kita akan menggunakan studi kasus "MyOrder App" (Portal Riwayat Pesanan Pelanggan). Berikut adalah pemetaan bagaimana setiap risiko muncul pada fitur aplikasi toko online:

Risiko OWASP Fitur Aplikasi MyOrder Skenario Celah jika Menggunakan Prompt Polos
A01: Access Control Detail Pesanan (/order?id=101) User A mengganti ID ke id=102 dan bisa melihat alamat & belanjaan User B.
A02: Kriptografi Registrasi Akun Pelanggan AI menyimpan password langsung sebagai plaintext di database.
A03: SQL Injection Pencarian Barang / Produk Mengetik ' OR '1'='1 menampilkan semua produk rahasia / diskon internal.
A04: Insecure Design Klaim Kupon Diskon / OTP Penyerang menebak ribuan kode voucher otomatis tanpa ada batasan percobaan.
A05: Misconfiguration Pesan Error saat Gagal Bayar Layar menampilkan error SQL mentah dan nama tabel database ke pembeli.
A07: Autentikasi Halaman Login Pembeli Bebas ditebak brute force tanpa batas percobaan & sesi berlaku selamanya.

📍 Fase 1: Pembangunan Baseline Aplikasi (Kode Awal AI yang Rentan)

Langkah pertama: Minta AI membuatkan prototipe aplikasi awal. Kita akan melihat bagaimana AI menghasilkan kode yang "langsung jalan" namun menyimpan banyak celah keamanan secara default.

🤖 PROMPT LAB 1: MEMBUAT PROTOTIPE BASELINE APLIKASI 
Saya ingin membuat aplikasi web sederhana "MyOrder - Portal Cek Pesanan" menggunakan HTML, CSS, JavaScript, dan backend sederhana (Node.js/Express atau mock database JSON).

Fitur yang dibutuhkan:
1. Registrasi dan Login User (nama, email, password).
2. Dashboard pembeli: Menampilkan daftar riwayat pesanan milik user.
3. Halaman Detail Pesanan: Mengambil data pesanan berdasarkan parameter URL (?order_id=...).
4. Kotak Pencarian Produk: Mencari barang belanjaan berdasarkan nama.

Tolong buatkan kode lengkapnya agar bisa langsung saya jalankan di laptop.

📍 Fase 2: Simulasi Penyerangan (Hands-on Pentesting Mandiri)

Setelah aplikasi berjalan di browser, uji coba 3 skenario serangan berikut untuk membuktikan keberadaan celah keamanan:

🎯 Uji Coba 1: Bobol Data Orang Lain (A01)

Buka 2 tab browser. Login sebagai User A (Order ID: 101) dan User B (Order ID: 102). Di tab User A, ubah angka URL menjadi /order?id=102. Amati: Anda berhasil melihat alamat dan struk belanja milik User B!

💉 Uji Coba 2: SQL Injection (A03)

Ketik karakter ' OR '1'='1 di kolom pencarian produk. Amati: Sistem menampilkan seluruh data produk privat atau memunculkan pesan error database mentah.

🔓 Uji Coba 3: Brute Force Login (A07)

Coba login dengan password salah sebanyak 10 kali berturut-turut. Sistem tetap membiarkan Anda mencoba tanpa ada peringatan atau penguncian akun sementara.

📍 Fase 3: Hardening Keamanan Menggunakan Master Prompt OWASP

Sekarang, gunakan prompt berbasis standar OWASP untuk meminta AI menambal seluruh celah tersebut secara tuntas:

🛡️ PROMPT LAB 2: HARDENING ACCESS CONTROL & SQL INJECTION 
Aplikasi MyOrder saya memiliki 2 celah kritis:
1. User bisa melihat pesanan milik orang lain hanya dengan mengganti nomor order_id di URL (OWASP A01).
2. Fitur pencarian rawan SQL Injection (OWASP A03).

Ini kode aplikasi saya saat ini:
[TEMPEL KODE CONTROLLER / BACKEND ANDA DI SINI]

Tolong perbaiki dengan syarat wajib:
1. Validasi kepemilikan data: Pastikan order_id yang diminta BENAR-BENAR milik user_id yang sedang login dari session. Jika bukan, tolak dengan response 403 Forbidden.
2. Ubah semua query database menjadi Parameterized Query / Prepared Statements.
3. Jelaskan baris mana yang Anda ubah dan kenapa perubahan itu membuat aplikasi aman.
🔐 PROMPT LAB 3: HARDENING PASSWORD HASHING & RATE LIMITER 
Tolong tambahkan proteksi autentikasi (OWASP A02 & A07) pada fitur registrasi dan login aplikasi MyOrder saya:
1. Gunakan bcrypt untuk hashing password sebelum disimpan ke database.
2. Tambahkan Rate Limiter: Maksimal 5 kali percobaan login gagal dalam 15 menit per IP, lalu kunci sementara.
3. Batasi masa berlaku sesi (JWT / session cookie) maksimal 2 jam dan revoke token saat user menekan Logout.
4. Gunakan pesan error generik: "Email atau password salah" (jangan beri tahu apakah email terdaftar atau tidak).

3. Berikan Skor Keamanan (1-100) dan rekomendasi checklist sebelum aplikasi ini dipublikasikan ke internet.

4 Tips Praktis Keamanan untuk Vibe Coder Non-IT

Prinsip dasar agar aplikasi Anda selalu terlindungi di dunia nyata.

  • Jangan Cuma Minta Fitur: Selalu sertakan kata kunci keamanan spesifik dalam prompt Anda (misalnya: "gunakan parameterized query, bcrypt hash, dan validasi kepemilikan data").
  • Audit Sebelum Go-Live: Jalankan Universal Security Prompt di atas sebelum aplikasi Anda diakses oleh pengguna umum di internet publik (production).
  • Perlakukan Data Pribadi dengan Standar Tinggi: Jika aplikasi Anda menyimpan nama, email, nomor HP, atau data transaksi, gunakan brankas Environment Variables dan proteksi database Row Level Security (RLS).
  • Gunakan Keamanan Berlapis (Defense in Depth): Validasi di sisi tampilan (frontend) berguna untuk kenyamanan user, tapi validasi di sisi server (backend) adalah benteng pertahanan yang sesungguhnya.
