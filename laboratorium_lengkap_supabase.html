2 Fase 2 · Skema SQL DDL, UUID & Index
🎯 Sasaran: Supabase SQL Editor
📚 Teori: Foreign Key ke auth.users & Cascade Delete

Supabase mengelola pengguna di skema internal auth.users. Kolom user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE menjamin ketika akun user dihapus, semua data miliknya otomatis terhapus bersih tanpa data sampah.

💡 Mengapa Index Wajib Dibuat?

Perintah CREATE INDEX ON tabel(user_id); membuat daftar indeks cepat pada kolom user_id. Tanpa index, database harus men-scan jutaan baris data setiap kali ada pemanggilan query.

3 Fase 3 · Row Level Security (RLS Policies)
🎯 Sasaran: PostgreSQL Security Policies
📚 Teori: Cara Kerja RLS di PostgreSQL

Saat RLS aktif, PostgreSQL secara otomatis menyisipkan filter pada setiap query: WHERE user_id = auth.uid(). Fungsi auth.uid() membaca ID unik dari token JWT pengguna yang sedang aktif login.

🔐 USING vs WITH CHECK:

• USING (SELECT, UPDATE, DELETE): Menyaring baris data yang sudah ada.
• WITH CHECK (INSERT, UPDATE): Memvalidasi baris data baru sebelum disimpan ke tabel.

Fase 7 · Diagnostic Deteksi "Silent Bug" RLS (Data Tidak Muncul / Array Kosong [])
❓ Kenapa Hasil Query Selalu Kosong Tanpa Error?

Ini adalah kebingungan nomor 1 pemula: data di Supabase ada, tapi saat di-fetch dari frontend hasilnya selalu data = []. PostgreSQL menganggap ini filter keamanan RLS: baris disembunyikan karena belum login atau auth.uid() tidak cocok.

🔍 3 Langkah Cek Cepat Mandiri:

1. Cek apakah user sudah login (supabase.auth.getUser()).
2. Cek apakah policy FOR SELECT sudah dibuat.
3. Cek apakah user_id di tabel sama dengan UUID user yang login.

Data di tabel Supabase saya tidak muncul di frontend (hasil query selalu [] / kosong), padahal tidak ada error di console.
Bantu periksa 3 kemungkinan penyebab berikut secara to the point:
1. Apakah RLS aktif tapi policy SELECT belum dibuat atau pengguna belum login?
2. Apakah user_id di database cocok dengan auth.uid() pengguna yang sedang login?
3. Berikan SQL checklist untuk memeriksa status RLS dan list policy yang sedang aktif di tabel saya.

LAB 01 — SQL Schema & DDL (Data Definition Language)

Merancang struktur database PostgreSQL, relasi Foreign Key, UUID Primary Key, Triggers, dan Indexes.

📚 A. Teori Fundamental & Penjelasan Bahasa Awam

Database adalah tempat penyimpanan data permanen. Supabase didukung oleh PostgreSQL—mesin database kelas dunia yang digunakan oleh Netflix, Spotify, dan GitHub.

🏪 Analogi: Minimarket dengan Sistem Gudang

• GUDANG = Database PostgreSQL (gedung penyimpanan utama).
• RAK PRODUK = Tabel (profiles, categories, transactions).
• BARIS BARANG = Record (satu lembar data transaksi).
• LABEL RAK = Kolom / Field (nama, harga, tanggal).
• SATPAM OTOMATIS = Trigger (langsung buatkan kartu anggota saat pembeli baru mendaftar).

💡 Kamus Istilah Teknis Lab 01 dalam Bahasa Awam (Non-IT):
📐 DDL (Data Definition Language)

Artinya: Gambar cetak biru arsitek. Perintah untuk membuat "ruangan atau lemari formulir kosong" (tabel) sebelum data diisi.

🆔 UUID (Universal Unique ID)

Artinya: Nomor seri KTP unik acak 36 digit (misal: a1b2-c3d4...). Tidak bisa ditebak peretas, beda dengan angka urut 1, 2, 3 yang mudah dibobol.

🔗 Foreign Key & Cascade Delete

Artinya: Tali pengikat kepemilikan. Jika akun pengguna dihapus, semua data belanjaannya otomatis ikut dibakar bersih tanpa meninggalkan sampah.

⚡ Index

Artinya: Halaman daftar isi di belakang buku tebal. Membantu sistem menemukan data dalam hitungan sekejap mata tanpa harus membalik lembar satu per satu.

Istilah Teknis Definisi Sederhana Analogi Dunia Nyata
TABLE Tempat simpan satu jenis data terstruktur Rak khusus di gudang (misal: Rak Makanan, Rak Minuman)
PRIMARY KEY Nomor unik identitas setiap baris (UUID) Nomor barcode unik pada bungkus produk
FOREIGN KEY Kolom penunjuk pemilik data ke tabel lain Stiker nama pemilik yang ditempel di koper
TRIGGER Perintah otomatis saat suatu kejadian terjadi Pintu minimarket yang otomatis berbunyi menyambut tamu
INDEX Jalur pintas pencarian data super cepat Buku indeks pencarian cepat nomor telepon

LAB 02 — Row Level Security (RLS)

Mengisolasi akses data antar pengguna di level kernel database PostgreSQL dengan auth.uid().

📚 A. Teori Fundamental & Penjelasan Bahasa Awam

Row Level Security (RLS) adalah fitur PostgreSQL yang menentukan siapa yang boleh melihat/mengubah baris mana secara otomatis di server database.

🏦 Analogi: Brankas Pribadi vs Brankas Terbuka

• TANPA RLS: Semua orang membuka laci yang sama. Jika ada orang bertanya ke database, seluruh data rahasia milik semua pengguna di dunia langsung terbuka (Sangat Berbahaya!).
• DENGAN RLS: Setiap baris data diberi gembok sidik jari. Saat pengguna Budi login, PostgreSQL otomatis memfilter data sehingga Budi hanya bisa membuka dan melihat catatannya sendiri.

💡 Kamus Istilah Teknis Lab 02 dalam Bahasa Awam (Non-IT):
🔐 RLS (Row Level Security)

Artinya: Gembok per baris. Fitur keamanan di mana database menolak siapa pun yang mencoba mengintip baris data milik orang lain.

🪪 auth.uid()

Artinya: Sensor sidik jari digital. Fungsi otomatis yang membaca ID unik dari akun pengguna yang sedang login saat ini.

👓 USING (Filter Baca)

Artinya: Kacamata filter. Menentukan baris data mana saja yang boleh terlihat di layar pengguna.

🛡️ WITH CHECK (Filter Setor)

Artinya: Satpam pemeriksa barang masuk. Memastikan data baru yang dikirim pengguna memang mencantumkan ID pemilik yang sah.

Operasi Data Sintaks Kebijakan (Policy) Fungsi Validasi Awam
SELECT (Lihat Data) USING (user_id = auth.uid()) Baris mana saja yang boleh dibaca / dilihat
INSERT (Tambah Baru) WITH CHECK (user_id = auth.uid()) Data baru apa yang boleh disimpan
UPDATE (Ubah Nilai) USING (...) WITH CHECK (...) Baris mana yang boleh diubah isinya
DELETE (Hapus Data) USING (user_id = auth.uid()) Baris mana yang boleh dibuang

LAB 03 — .env Setup & Supabase Client Singleton

Konfigurasi variabel lingkungan yang aman di Vite + React TypeScript dan Singleton Pattern.

📚 A. Teori Fundamental & Penjelasan Bahasa Awam

Bagaimana cara menghubungkan aplikasi web di laptop ke server Supabase di cloud tanpa membocorkan kunci rahasia ke publik.

🔐 Analogi: Kartu Tamu Lobi vs Kunci Master Brankas

• Anon Key (VITE_SUPABASE_ANON_KEY): Ibarat kartu tamu di lobi hotel. Siapa pun boleh pegang, tetapi hanya bisa membuka pintu kamar miliknya sendiri sesuai aturan RLS.
• Service Role Key: Ibarat kunci master pemilik gedung yang bisa membuka semua pintu kamar. DILARANG KERAS ditaruh di kode frontend atau di-upload ke GitHub!

💡 Kamus Istilah Teknis Lab 03 dalam Bahasa Awam (Non-IT):
📞 Singleton Pattern

Artinya: Satu saluran telepon bersama. Daripada setiap tombol memasang kabel telepon baru ke database, kita pasang 1 saluran telepon utama yang dipakai bersama agar laptop tidak lemot.

📁 File .env (Environment Variables)

Artinya: Kertas catatan rahasia di laci pribadi. Menyimpan alamat URL dan kunci API agar tidak tertulis langsung di kode publik.

🏷️ Prefix VITE_

Artinya: Stempel izin baca. Di Vite, hanya variabel dengan awalan VITE_ yang diizinkan dibaca oleh browser.

🙈 .gitignore

Artinya: Daftar "Jangan Dibawa". Memerintahkan Git untuk tidak pernah mengirim file .env.local ke GitHub publik.

🟢 Presence

// 2. QUERY BUILDER (SELECT)

  .from('transactions')
  .select('*, categories(name, color)')

  .order('date', { ascending: false })
  .limit(20);

// 3. INSERT & OPTIMISTIC

  .from('transactions')
  .insert({ user_id: user.id, amount: 50000, type: 'expense' })

// 4. STORAGE
await supabase.storage.from('avatars').upload(path, file, { upsert: true });
const { data: { publicUrl } } = supabase.storage.from('avatars').getPublicUrl(path);

// 5. REALTIME (SELALU CLEANUP!)
const channel = supabase.channel('realtime_tx')
  .on('postgres_changes', { event: 'INSERT', table: 'transactions' }, (payload) => {
    // update state
  })
  .subscribe();
supabase.removeChannel(channel); // <- WAJIB saat unmount!
