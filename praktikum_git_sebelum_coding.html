P5.1

Inisialisasi Repo Git + Struktur Proyek Awal

git init · .gitignore · README.md · Commit Pertama · Verifikasi Status

📍 Konteks: Ini adalah langkah pertama yang wajib dilakukan sebelum menulis satu baris kode pun. Git harus sudah aktif dari detik pertama proyek dibuat — bukan di akhir setelah banyak perubahan terjadi.
🎯
Yang akan kamu pelajari: Cara mengecek apakah Git sudah terinstal, cara memulai repo baru, membuat pelindung file rahasia (.gitignore), dan melakukan commit pertama kamu.
📋 Prompt P5.1 — Paste ke Antigravity AI IDE 
[ROLE]: Senior Developer yang mengajarkan Git kepada pemula absolute
[CONTEXT]: Aku baru saja membuat folder proyek kosong bernama "proyek-web-ku" di laptop Windows-ku. Aku belum pernah menggunakan Git sama sekali. Aku menggunakan Antigravity AI IDE.
[INSTRUCTION]:
Bantu aku menyiapkan Git dari nol dengan langkah berikut:
1. Cek apakah Git sudah terinstal (berikan perintah terminalnya + apa artinya output yang muncul).
2. Jika Git belum terinstal, berikan instruksi cara menginstalnya di Windows (step by step, sertakan link download resmi).
3. Inisialisasi repo Git di folder "proyek-web-ku" — jalankan perintahnya, jelaskan apa yang terjadi di balik layar.
4. Buat file .gitignore dasar yang aman untuk proyek web (node_modules, .env, .DS_Store, dist/, .vscode/, dll). Jelaskan fungsi setiap baris.
5. Buat file README.md sederhana berisi nama proyek "proyek-web-ku" dan deskripsi singkat 2-3 kalimat.
6. Lakukan commit pertama dengan pesan "inisialisasi proyek" dan verifikasi hasilnya.
7. Tampilkan output `git log --oneline` dan bantu aku membacanya.
[CONSTRAINT]:
- Jelaskan setiap perintah terminal dengan analogi sederhana, seolah aku berusia 12 tahun.
- Gunakan bahasa Indonesia yang ramah dan tidak teknikal.
- Tampilkan perintah terminal dalam blok kode yang jelas dan bisa langsung disalin.
- Jangan lewatkan langkah apapun — anggap aku zero knowledge.
✅
Verifikasi Keberhasilan
Setelah prompt selesai, ketik git log --oneline di terminal. Jika muncul 1 baris dengan teks "inisialisasi proyek", kamu berhasil! Folder proyekmu kini punya "mesin waktu" yang aktif.

P5.2

Memahami Siklus Kerja: Edit → Stage → Commit

git status · git add · git diff · Commit Message yang Baik & Buruk

📍 Konteks: Setelah repo siap, kamu perlu menguasai ritme kerja harian: edit kode → pilih file yang mau disimpan → simpan snapshot. Ritme ini akan kamu lakukan puluhan kali setiap hari. Semakin terbiasa, semakin aman proyekmu.
💡
Analogi Staging Area: Bayangkan kamu punya meja kerja (file yang sudah diedit), keranjang foto (staging area / git add), dan album foto (commit). Kamu bisa pilih mana yang masuk keranjang sebelum difoto — tidak semua harus masuk sekaligus.
📋 Prompt P5.2 — Paste ke Antigravity AI IDE 
[ROLE]: Git Coach yang mengajarkan workflow harian kepada pemula
[CONTEXT]: Aku sudah berhasil membuat repo Git pertamaku dan punya 1 commit. Sekarang aku ingin belajar siklus kerja sehari-hari — cara menyimpan perubahan kode dengan benar. Aku sudah membuat file index.html sederhana berisi teks "Hello World".
[INSTRUCTION]:
Ajarkan aku siklus kerja Git harian dengan praktik langsung, langkah demi langkah:

Langkah 1: EDIT FILE
- Buka file index.html dan tambahkan satu paragraf baru (berikan contoh HTML yang harus aku ketik).
- Simpan file-nya.

Langkah 2: LIHAT PERUBAHAN
- Jalankan `git status` — jelaskan dengan detail apa artinya warna merah dan hijau yang muncul.
- Jalankan `git diff` — ajarkan cara membacanya (apa arti tanda + berwarna hijau dan - berwarna merah).

Langkah 3: STAGING
- Jalankan `git add index.html` — jelaskan apa perbedaannya dengan `git add .`.
- Jalankan `git status` lagi — tunjukkan perbedaan kondisi sebelum dan sesudah `git add`.

Langkah 4: COMMIT
- Lakukan commit dengan pesan yang baik.
- Jelaskan format commit message profesional yang bisa aku ikuti.
- Berikan 5 contoh commit message yang BAIK dan 5 yang BURUK.

Langkah 5: VERIFIKASI
- Jalankan `git log --oneline` — ajarkan cara membaca riwayat commit.
- Sekarang kita punya 2 commit! Jelaskan artinya.

[CONSTRAINT]:
- Gunakan analogi "buku catatan harian" untuk menjelaskan staging area.
- Jelaskan kenapa commit message yang jelas itu penting saat debugging di masa depan.
📌
Commit Message: Baik vs Buruk
❌ Buruk: "update", "fix", "asdf", "coba lagi"
✅ Baik: "tambah navbar dengan logo dan 3 menu utama", "perbaiki bug tombol submit tidak responsif di mobile"

📋 Prompt P5.3 — Paste ke Antigravity AI IDE 
[ROLE]: Git Recovery Specialist yang mengajarkan pemulihan kode darurat
[CONTEXT]: Aku sudah punya 2 commit di repo-ku. Aku ingin berlatih memulihkan kode yang rusak karena AI salah mengubah file. Ini simulasi emergency recovery — aku perlu tahu cara kembali ke kondisi aman dalam hitungan detik.
[INSTRUCTION]:
Pandu aku melalui 3 skenario pemulihan Git yang paling sering dibutuhkan:

═══ SKENARIO A — Batalkan perubahan yang BELUM di-commit ═══
Situasi: AI baru saja mengubah file-fileku tapi hasilnya buruk, dan aku belum commit.
1. Instruksikan aku untuk merusak file index.html secara manual (hapus semua isinya, ganti dengan teks acak "RUSAK RUSAK RUSAK").
2. Tampilkan kondisi rusaknya dengan `git status` dan `git diff`.
3. Berikan perintah yang tepat untuk memulihkan file ke kondisi sebelumnya.
4. Verifikasi file kembali normal dengan membuka isinya.
5. Jelaskan kapan harus pakai `git checkout .` vs `git restore .`

═══ SKENARIO B — Kembali ke versi commit tertentu (tanpa hapus riwayat) ═══
Situasi: AI sudah melakukan banyak perubahan, dan aku sudah commit hasilnya, tapi sekarang menyesal.
1. Tampilkan daftar semua commit dengan `git log --oneline`.
2. Jelaskan cara membaca HASH commit (kode unik 7 karakter di sebelah kiri).
3. Gunakan `git checkout  -- index.html` untuk mengambil versi file dari commit pertama.
4. Commit ulang perubahan pemulihan tersebut dengan pesan "recovery: kembali ke versi awal index.html".
5. Jelaskan perbedaan `git checkout`, `git revert`, dan `git reset` — kapan masing-masing dipakai.

═══ SKENARIO C — Investigasi: Cek apa yang berubah tanpa memulihkan ═══
Situasi: Aku curiga ada yang berubah tapi tidak yakin. Aku ingin lihat dulu sebelum memutuskan.
1. Bandingkan kondisi file sekarang vs commit pertama dengan `git diff  index.html`.
2. Tampilkan perbedaannya baris per baris dan ajarkan cara membacanya.
3. Tampilkan seluruh isi file dari commit tertentu tanpa mengubah apapun.

[CONSTRAINT]:
- Gunakan analogi "tombol undo di dokumen Word" untuk menjelaskan perbedaan metode recovery.
- Sertakan peringatan jelas untuk tindakan yang TIDAK bisa di-undo.
- Ingatkan aku untuk selalu commit sebelum meminta AI melakukan perubahan besar.
⚠️
Peringatan Penting: Perintah git checkout . atau git restore . akan menghapus permanen semua perubahan yang belum di-commit. Tindakan ini TIDAK BISA di-undo! Pastikan kamu benar-benar ingin membuang semua perubahan tersebut sebelum menjalankannya.
🔑
Aturan Emas setelah P5.3: Setiap kali kamu hendak mengetik prompt ke AI, berhenti sebentar → buka terminal → ketik git add . dan git commit -m "checkpoint sebelum fitur X" → baru minta AI bekerja. Jadikan ini refleks!
P5.4

Strategi Commit Cerdas: Kapan & Seberapa Sering Commit?

Atomic Commit · Checkpoint Strategy · AI Safety Protocol · Alias Terminal

📍 Konteks: Banyak pemula commit terlalu jarang (hanya sekali di akhir hari) atau tidak tahu kapan waktu yang tepat. Prompt ini mengajarkan strategi commit yang tepat khusus untuk Vibe Coder — pengguna yang bekerja bersama AI IDE.
🎮
Analogi Video Game: Commit adalah "titik simpan" (save point). Bayangkan kamu bermain RPG dan tidak pernah klik simpan — satu mati dan kamu mulai dari awal! Vibe Coder yang baik commit sesering pemain game yang menekan tombol simpan.
📋 Prompt P5.4 — Paste ke Antigravity AI IDE 
[ROLE]: Vibe Coding Mentor dengan keahlian Git Workflow untuk pengguna AI IDE
[CONTEXT]: Aku sudah bisa melakukan commit Git. Sekarang aku bingung kapan waktu yang tepat untuk commit. Aku sering lupa commit dan baru ingat setelah mengerjakan banyak hal sekaligus. Aku bekerja menggunakan Antigravity AI IDE.
[INSTRUCTION]:
Ajarkan aku strategi commit yang tepat untuk Vibe Coder:

1. 5 TRIGGER WAJIB COMMIT — kapan harus commit tanpa tanya:
   - Sebelum meminta AI melakukan perubahan besar atau multi-file
   - Setelah satu fitur kecil berhasil berfungsi di browser
   - Sebelum mencoba eksperimen baru yang belum pernah dilakukan
   - Setelah memperbaiki satu bug
   - Di akhir setiap sesi kerja (sebelum menutup laptop)

2. ATOMIC COMMIT — jelaskan konsep "satu commit = satu perubahan logis" dengan:
   - Contoh BENAR: commit terpisah untuk navbar, commit terpisah untuk form, commit terpisah untuk CSS.
   - Contoh SALAH: satu commit berisi perubahan navbar + form + CSS + database sekaligus.
   - Mengapa atomic commit memudahkan debugging?

3. PRAKTIK LANGSUNG — pandu aku membuat 3 commit terpisah:
   a) "tambah struktur HTML dasar halaman utama"
   b) "tambah style CSS dasar untuk layout"
   c) "checkpoint: siap minta AI tambah fitur form kontak"

4. FORMAT COMMIT MESSAGE PROFESIONAL:
   - Berikan template: [kata kerja] + [objek yang diubah] + [konteks opsional]
   - Berikan 10 contoh commit message yang baik untuk proyek web pemula.
   - Berikan contoh commit message untuk "checkpoint sebelum minta AI".

5. BUAT ALIAS SHORTCUT:
   - Ajarkan cara membuat alias `git add . && git commit -m ""` menjadi lebih singkat.
   - Berikan perintah cara membuat alias di Windows (Git Bash atau PowerShell).

[CONSTRAINT]:
- Gunakan analogi "titik simpan di video game" untuk atomic commit.
- Berikan template checklist singkat yang bisa aku tempel di meja sebagai pengingat.
- Tekankan pentingnya commit SEBELUM meminta AI bekerja (bukan sesudah).
🖨️ Template Checklist — Print & Tempel di Meja!
  • Satu fitur kecil berhasil? → COMMIT!
  • Mau minta AI ubah banyak file? → COMMIT dulu!
  • Mau coba sesuatu yang berisiko? → COMMIT dulu!
  • Baru saja perbaiki bug? → COMMIT!
  • Mau tutup laptop? → COMMIT!

⚡ Perintah cepat: git add . && git commit -m "pesan kamu"

P5.5

Git Log: Membaca Riwayat & Investigasi Perubahan AI

git log · git show · git diff antara commit · Audit Trail AI Changes · git bisect

📍 Konteks: Setelah punya banyak commit, kamu perlu bisa "membaca peta" riwayatmu. Kemampuan ini sangat berguna saat debugging — kamu bisa lacak kapan tepatnya bug pertama kali muncul, dan perubahan apa yang AI lakukan saat itu.
📹
Analogi CCTV: Git log adalah rekaman CCTV proyekmu. Setiap commit adalah satu frame rekaman. Kamu bisa rewind, play, dan zoom in ke moment tertentu untuk melihat persis apa yang terjadi dan siapa yang mengubah apa.
📋 Prompt P5.5 — Paste ke Antigravity AI IDE 
[ROLE]: Git Detective yang mengajarkan investigasi riwayat kode
[CONTEXT]: Aku sudah punya minimal 5 commit di repo-ku dari latihan tadi. Aku ingin belajar cara membaca riwayat Git untuk keperluan debugging dan audit perubahan yang dilakukan AI. Selama ini aku hanya bisa commit tapi tidak tahu cara "membaca" riwayatnya.
[INSTRUCTION]:
Ajarkan aku cara membaca dan menggunakan riwayat Git secara efektif:

1. BERBAGAI FORMAT LOG — praktikkan satu per satu dan jelaskan outputnya:
   - `git log` → format lengkap, jelaskan setiap bagian (hash, author, date, message)
   - `git log --oneline` → format ringkas, bagus untuk overview cepat
   - `git log --oneline --graph` → tampilan pohon visual, jelaskan simbolnya (*, |, \)
   - `git log --oneline -5` → tampilkan hanya 5 commit terakhir

2. INSPEKSI DETAIL SATU COMMIT:
   - Ambil hash salah satu commitku dari `git log --oneline`
   - `git show ` → tampilkan semua perubahan di commit itu, ajarkan cara membacanya
   - `git diff  ` → bandingkan dua commit berbeda
   - Praktikkan dengan commit-commitku yang nyata

3. LACAK RIWAYAT FILE SPESIFIK:
   - `git log --follow -p index.html` → lihat seluruh riwayat perubahan satu file
   - Jelaskan kapan perintah ini berguna (debug, audit perubahan AI)
   - Cara menghentikan output panjang (tekan Q)

4. TEMUKAN KAPAN BUG MASUK — Konsep git bisect:
   - Jelaskan konsep git bisect dengan analogi "tebak berapa" (binary search di antara commit)
   - Berikan skenario contoh kasusnya: "website jadi lambat setelah 10 commit terakhir"
   - Tidak perlu praktik, cukup konsep yang mudah dipahami

5. LAPORAN HARIAN DENGAN AI:
   - Tampilkan output `git log --oneline` dari sesi kita hari ini
   - Minta AI membuat ringkasan narasi: "Apa saja yang sudah aku kerjakan hari ini berdasarkan commit log ini?"

[CONSTRAINT]:
- Gunakan analogi CCTV untuk menjelaskan git log.
- Ajarkan cara menghentikan tampilan log panjang (tekan Q di terminal).
- Berikan tips cara membaca output `git log` yang terlihat menakutkan bagi pemula.
🔍
Tips: Membaca Git Log yang "Menakutkan"
Output git log penuh teks? Jangan panik! Tekan Q untuk keluar. Gunakan git log --oneline untuk tampilan yang lebih ramah. Setiap baris = satu commit = satu "titik aman" yang bisa kamu kembali ke sana.
