💡 Prinsip Kunci: Jangan pernah memperbaiki bug saat sedang menguji manual. Selesaikan seluruh skenario terlebih dahulu untuk mengetahui kondisi kesehatan aplikasi secara utuh, baru lakukan perbaikan satu per satu secara terisolasi (Atomic Fix).
🏠 Tukang vs Inspektur Bangunan
AI adalah tukang bangunan cerdas yang memasang dinding dan instalasi pipa sesuai gambar denah. Pengujian manual adalah saat Anda masuk ke rumah: membuka setiap pintu, menyalakan keran air bersama saklar lampu, dan memastikan pipa tidak bocor.
⚡ Happy Path vs Edge Cases
Happy Path: Pengguna mengisi form dengan sempurna.
Edge Cases: Pengguna mengklik tombol 5x cepat, submit field kosong, atau memasukkan karakter aneh. Pengguna nyata selalu menemukan kasus tepi lebih dulu!
🎯 Prinsip Atomic Bug Fixing
Perbaiki satu bug per satu prompt terarah. Menggabungkan 5 keluhan bug dalam satu perintah membuat AI merombak seluruh file dan memicu bug baru (code regression).

FASE 1

Dekonstruksi PRD ke Matriks Skenario Uji (25 Menit)

Setiap fitur yang tercantum pada dokumen prd.md Anda wajib memiliki minimal 2 skenario uji: 1 alur normal (Happy Path) dan minimal 1 kasus ekstrem (Edge Case).

📋 MASTER PROMPT 1: GENERATE TEST PLAN DARI PRD
Bertindaklah sebagai Senior QA Lead & Security Tester profesional. Saya memiliki dokumen PRD / daftar fitur aplikasi saya sebagai berikut: [TEMPELKAN DAFTAR FITUR DARI prd.md ATAU DESKRIPSI APLIKASI ANDA DI SINI] Tugas Anda: Buatkan file komprehensif `test-plan.md` dalam format tabel Markdown berstandar industri yang mencakup: 1. Skenario Happy Path (alur normal setiap fitur) 2. Skenario Edge Cases (input kosong, batasan angka, karakter aneh, double click) 3. Skenario Penanganan Error & Keamanan Dasar Format kolom tabel yang wajib digunakan: | ID | Fitur | Kategori | Skenario Uji | Langkah Pengujian | Hasil yang Diharapkan | Status | Catatan Bug | Instruksi Tambahan: - Beri status default: "⚠️ BELUM DIUJI" - Sertakan struktur bagian "Temuan Bug (Bug Log)" dan "Ringkasan Metrik Kelayakan Rilis" di bagian bawah file. - Simpan file ini langsung ke root workspace dengan nama `test-plan.md`.
✅ Output yang Benar (Sesuai Standar)
File test-plan.md tersimpan di root dengan tabel terstruktur, mencakup minimal 10 skenario uji (fitur autentikasi, transaksi, form input, dan respon error).
❌ Jebakan yang Harus Dihindari
Membuat skenario yang terlalu umum seperti "Coba semua tombol" tanpa langkah reproduksi dan ekspektasi hasil yang jelas.
FASE 2

Eksekusi Pengujian Manual & 6 Edge Cases Wajib (50 Menit)

⚡ 6 Kategori Kasus Ekstrem Wajib Uji:

1. Input Kosong & Whitespace

Kirim form tanpa isi apapun atau hanya spasi (" "). Form wajib menolak!

2. Batasan Angka & Teks

Input angka `-1`, `0`, atau `999999999`. Paste 1000 karakter pada nama.

3. Karakter Berbahaya

Ketik `<script>alert(1)</script>` atau `' OR '1'='1`. Pastikan aman XSS.

4. Spam Klik Cepat (Double-Click)

Klik tombol 'Simpan' / 'Bayar' 3x cepat. Cegah data kembar / double charge.

5. Refresh & Navigasi Balik

Tekan F5 saat form sedang diisi. Pastikan session dan state tidak crash.

6. Simulasi Offline (DevTools)

Set Network ke Offline pada Chrome DevTools. Harus muncul pesan ramah.

🚦 Matriks Derajat Keparahan Bug (Severity Matrix):

🔴 Critical (Blokir Rilis: Crash / Data Hilang) 🟠 High (Fitur Utama Macet, Ada Workaround) 🟡 Medium (Logika / Format Pesan Salah) 🔵 Low (Kosmetik / Typo / Geser 2px)
📋 MASTER PROMPT 2: EKSPLORASI DEEP EDGE CASES
Aplikasi saya memiliki fitur: [JELASKAN FITUR, CONTOH: "Checkout Belanja & Upload Bukti Pembayaran"]. Tolong daftarkan 8 kasus ekstrem (edge cases) paling berbahaya yang berpotensi merusak fitur ini atau membuat data di database korup. Kategorikan berdasarkan: 1. Validasi Input (Format, Tipe File, Batas Ukuran) 2. Asinkron & Jaringan (Timeout, Double Submit) 3. Keamanan & Izin Akses (RLS Supabase / Token Expired) Format jawaban dalam tabel siap tempel ke file `test-plan.md`.
FASE 3

Atomic Bug Fixing & Uji Regresi (35 Menit)

❌ Kode Rentan (Sebelum Perbaikan) Bug Double Submit
// Masalah: Tombol tidak di-lock saat proses async function handleSaveData(payload) { showSpinner(); // Jika user klik 3x cepat, // request ini dikirim 3 kali! const { data, error } = await supabase .from('orders') .insert(payload); hideSpinner(); if (!error) showToast("Tersimpan!"); }
✅ Kode Aman (Atomic Lock Guard) Anti Double Click
let isSubmitting = false; async function handleSaveData(payload) { if (isSubmitting) return; // Guard isSubmitting = true; const btn = document.getElementById('btn-submit'); if (btn) btn.disabled = true; try { showSpinner(); const { error } = await supabase .from('orders') .insert(payload); if (error) throw error; showToast("Berhasil disimpan!"); } finally { isSubmitting = false; if (btn) btn.disabled = false; hideSpinner(); } }
📋 MASTER PROMPT 3: TARGETED ATOMIC BUG FIX
Saya menemukan bug pada aplikasi saya saat menjalankan test plan: - ID Bug / Skenario: [BUG-01 / TC-05] - Fitur: [Nama Fitur, contoh: Tombol Simpan Transaksi] - Langkah Reproduksi: [Klik tombol Simpan 3x sangat cepat] - Hasil Aktual: [Muncul data ganda / duplikat di database] - Hasil Diharapkan: [Hanya 1 data yang tersimpan, tombol otomatis disabled saat proses simpan] Instruksi Perbaikan: 1. Perbaiki HANYA bagian fungsi atau file yang bertanggung jawab atas masalah ini. 2. JANGAN mengubah struktur komponen lain yang sudah berjalan normal. 3. Jelaskan solusi dalam 2 kalimat, lalu tampilkan kode perbaikannya.
