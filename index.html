Modul 5: Git Sebelum Coding — Jaring Pengaman Wajib Vibe Coder

Bangun Halaman Pertama 90 menit Modul Praktikum Terpisah

Tujuan: Peserta memahami mengapa Git adalah keharusan sebelum mengizinkan AI menyentuh kode, punya jaring pengaman, dan menguasai alur kerja commit hingga pemulihan kode yang dirusak AI.

⚡ Modul Mandiri Pertemuan 5
Materi Lengkap Tersedia di Halaman Khusus:
🌳 Buka Lab Praktikum Git (P5)

📚 Teori

  • Git = Mesin Waktu Proyek: Analogi foto snapshot di kamera polaroid sebelum merenovasi ruangan
  • Bahaya Tanpa Git: AI tidak punya tombol "undo" — satu prompt yang salah bisa merusak file tanpa titik kembali
  • Kamus 5 Istilah Git: Repository (gudang), Commit (snapshot simpan), Staging (pilih file foto), Branch (cabang), Checkout (kembali ke aman)
  • Aturan Emas Vibe Coder: "Commit sebelum minta AI melakukan perubahan besar" — jadikan ini refleks wajib
  • Siklus Kerja Aman: Mulai sesi → Kerjakan fitur kecil → 📸 COMMIT → Minta AI bantu → Cek hasil di browser

🧑‍💻 Praktikum — 5 Prompt AI

💡 Buka halaman modul praktikum lengkap untuk menyalin 5 prompt siap pakai ini.

  • Prompt 1 (P5.1): Inisialisasi repo Git, buat .gitignore aman, README.md, dan commit pertama
  • Prompt 2 (P5.2): Kuasai siklus harian git status, git diff, git add, dan commit message profesional
  • Prompt 3 (P5.3) ⭐: Simulasi AI rusak kode & pemulihan darurat dalam 5 detik (git checkout, git restore)
  • Prompt 4 (P5.4): Strategi Atomic Commit, 5 trigger wajib commit, dan checklist video game save point
  • Prompt 5 (P5.5): Membaca riwayat git log --oneline, inspeksi perubahan AI, dan audit trail
!

Peringatan Pemulihan: Latihan pemulihan Git (git checkout . atau git restore .) menghapus perubahan yang belum di-commit secara permanen. Pastikan commit snapshot aman terlebih dahulu sebelum mencoba perintah revert.

Output pertemuan Repo Git lokal dengan .gitignore, README.md, dan minimal 5 commit bermakna — termasuk satu commit pemulihan dari kerusakan simulasi.
Kesalahan yang sering terjadi Hanya commit sekali di akhir hari — jaring pengaman jadi tidak berguna saat kode hancur di tengah. Commit sesering mungkin!

Modul 6: Push Project ke GitHub — Backup, Portofolio & Kolaborasi Cloud

Bangun Halaman Pertama 90 menit Modul Praktikum Terpisah

Tujuan: Proyek lokal terhubung dan terunggah aman ke GitHub Cloud — memiliki standar pesan Conventional Commits, etalase README.md profesional, branch main terstandar, dan mampu sinkronisasi pull & perbaikan error push.

⚡ Modul Mandiri Pertemuan 6
Materi Lengkap Tersedia di Halaman Khusus:
☁️ Buka Modul Push GitHub (P6)

📚 Teori

  • GitHub Cloud: Mengapa repo di laptop bukan cadangan aman jika laptop rusak/hilang — cloud adalah etalase portofolio publik
  • Conventional Commits: Standar format pesan commit profesional (feat:, fix:, docs:, refactor:, style:)
  • README.md Standard: Elevator pitch, daftar fitur berikon, tech stack, dan instruksi instalasi lokal
  • Remote Origin & Upstream: Mendaftarkan URL GitHub (git remote add origin) dan mengunci pelacakan upstream (-u)
  • Alur Sinkronisasi Cloud: First Push, Daily Push 1-Langkah, git pull, serta resolusi merge conflict

🧑‍💻 Praktikum — 7 Modul Cloud Push

💡 Buka halaman modul praktikum lengkap untuk menyalin prompt siap pakai ini.

  • Standar Wajib: Pembuatan pesan commit berformat Conventional Commits
  • Prompt 1 (P6.1): Generator file README.md portofolio profesional via AI
  • Prompt 2 (P6.2): Hubungkan repo lokal ke remote origin & set branch main
  • Prompt 3 (P6.3): First push unggah perdana (git push -u origin main)
  • Prompt 4 (P6.4): Alur push rutin harian 1-langkah (Stage → Commit → Push)
  • Prompt 5 (P6.5): Sinkronisasi pembaruan & resolusi Merge Conflict (git pull)
  • Prompt 6 (P6.6): Dokter error push (diagnosis otomatis: rejected non-fast-forward, rebase, token)
!

Cek sebelum push: Jalankan git status dan pastikan tidak ada file yang mengandung password, API key, atau kredensial rahasia yang ikut masuk ke dalam commit. Sekali ter-push ke repo publik, kunci harus segera di-revoke.

Output pertemuan Repo GitHub live dengan README.md terisi, .gitignore aman, dan seluruh commit riwayat proyek berformat Conventional Commits.
Kesalahan yang sering terjadi Lupa menambahkan .env.local ke .gitignore sebelum push — API key bocor ke publik dan harus di-rotate ulang.

Konsep #1 — Database

Supabase & PostgreSQL: Gudang Data Milikmu

🏪
Analogi: Bayangkan Sebuah Minimarket

Database itu seperti gudang minimarket. Setiap jenis produk disimpan di rak yang berbeda — snack di rak A, minuman di rak B, produk kebersihan di rak C. Dalam database, "rak" ini disebut tabel. Setiap baris di rak adalah satu baris data (record). Dan setiap label harga, nama produk, jumlah stok — itulah kolom (field).

Supabase adalah layanan cloud yang menyediakan gudang (PostgreSQL) sekaligus kasir otomatis (API) — sehingga kamu tidak perlu membangun server gudang dari awal.

1
Tabel = Rak Gudang

Kita punya 3 tabel utama: profiles (data pengguna), categories (kategori transaksi), dan transactions (catatan uang masuk/keluar).

2
Foreign Key = Rak Terhubung

Setiap transaksi milik seorang user dan masuk dalam satu kategori. Foreign Key adalah cara memberi tahu database bahwa "rak ini terhubung ke rak itu".

3
Trigger = Satpam Otomatis

Saat user baru daftar, secara otomatis database akan membuat profil kosong untuknya. Ini dilakukan oleh Trigger — seperti satpam yang langsung memberi kartu anggota begitu tamu masuk.

4
Index = Katalog Pencarian

Tanpa index, database harus memeriksa setiap baris satu per satu (seperti cari produk tanpa katalog). Index adalah daftar isi yang membuat pencarian 10–100× lebih cepat.

💡 Insight Utama

PostgreSQL (mesin di balik Supabase) adalah salah satu database paling andal di dunia. Dipakai oleh perusahaan seperti Instagram, Spotify, dan GitHub. Dengan Supabase, kamu mendapat kekuatan enterprise-grade tanpa harus menjadi ahli server.

🔐
Konsep #2 — Row Level Security (RLS)

RLS: Gembok Per-Baris Data

🏦
Analogi: Brankas Bank

Bayangkan sebuah bank. Semua uang nasabah ada di satu brankas besar (database yang sama). Namun setiap nasabah hanya bisa mengambil uangnya sendiri — bukan milik orang lain. Itulah cara kerja Row Level Security (RLS).

Tanpa RLS, jika ada bug di aplikasi atau seseorang yang iseng memanggil API secara langsung, mereka bisa membaca data semua user sekaligus. Sangat berbahaya! RLS adalah lapisan keamanan di level database — bahkan jika aplikasimu punya bug, data tetap aman.

🔴 Tanpa RLS — Data Bocor!

Query sederhana:

SELECT * FROM transactions

PostgreSQL langsung mengembalikan semua baris dari semua pengguna tanpa filter. User A bisa melihat data User B!

⚠️ 1.000 transaksi dari 500 user dikembalikan semua
🟢 Dengan RLS — Aman!

Query yang sama:

SELECT * FROM transactions

PostgreSQL secara otomatis menambahkan filter tersembunyi: WHERE user_id = auth.uid(). User A hanya melihat datanya sendiri.

✅ Hanya 2 transaksi milik user yang login dikembalikan
🔑 3 Jenis Policy RLS yang Wajib Dipahami
SELECT Policy BACA — Siapa yang boleh melihat data? Jawaban: "Hanya pemilik data."
INSERT Policy TULIS — Siapa yang boleh menambah data? Jawaban: "User yang login, dan hanya dengan user_id miliknya sendiri."
UPDATE / DELETE Policy UBAH/HAPUS — Hanya pemilik data yang boleh mengubah atau menghapus datanya sendiri.
⚠️ Peringatan Penting

Jangan pernah mematikan RLS di production! Anggap RLS seperti helm saat berkendara — memang sedikit merepotkan saat setup, tapi tanpanya satu kecelakaan kecil bisa berakibat fatal. Semua tabel yang menyimpan data user WAJIB mengaktifkan RLS.

🔑
Konsep #3 — Authentication (Auth)

Auth: Sistem Masuk & Identitas Pengguna

🏨
Analogi: Hotel dengan Kartu Kunci

Ketika kamu check-in hotel, resepsionis memverifikasi identitasmu lalu memberi kartu kunci. Kartu ini memberimu akses ke kamarmu saja — bukan kamar orang lain, bukan dapur hotel, bukan ruang staff.

Supabase Auth bekerja persis seperti resepsionis dan kartu kunci tersebut. Saat user login (email/password, Google, dll.), Supabase memberi mereka sebuah token JWT — kartu digital yang berisi identitas mereka. Token ini dikirim bersama setiap request ke database, sehingga database tahu "siapa yang mengetuk pintu".

A
AuthContext

Komponen React yang menyimpan status login user di satu tempat terpusat. Semua halaman bisa tahu apakah user sudah login tanpa perlu mengecek ulang.

Dengan Vibe Coding + Supabase Auth, kamu tidak perlu belajar kriptografi, tidak perlu membuat sistem sesi sendiri, dan tidak perlu khawatir soal keamanan password. Cukup copy prompt → paste ke AI → jalankan, dan sistem autentikasi enterprise-level langsung jadi dalam menit!

Konsep #4 — Realtime Subscription

Realtime: Data yang Hidup & Bergerak Sendiri

📺
Analogi: Siaran TV vs. DVD

Cara kerja website biasa seperti memutar DVD — kamu tekan play, video dimulai, selesai. Jika ingin film baru, kamu harus keluar dan beli DVD baru (refresh halaman).

Realtime seperti siaran TV langsung — begitu ada siaran baru, langsung muncul di layarmu tanpa kamu perlu melakukan apa-apa. Data database berubah? Halaman webmu otomatis terupdate — persis seperti notifikasi WhatsApp yang langsung muncul tanpa kamu refresh aplikasi.

🎯 Kapan Kamu Butuh Fitur Realtime?
💬 Aplikasi Chat

Pesan baru muncul seketika di layar semua peserta tanpa reload.

📊 Dashboard Monitoring

Grafik penjualan atau statistik terupdate secara live setiap detik.

🛒 Stok Produk

Jika stok berubah di satu tab, tab lain langsung menampilkan stok terbaru.

🔔 Notifikasi

Sistem notifikasi yang muncul saat data di database berubah.

⚙️ Cara Kerja Realtime di Balik Layar
1 Aplikasimu membuka koneksi WebSocket ke Supabase (seperti membuka telepon dan membiarkan sambungan terbuka).
2 Kamu mendaftarkan "channel" untuk mendengarkan perubahan pada tabel tertentu — misalnya tabel transactions.
3 Saat ada data baru masuk ke tabel tersebut, Supabase langsung mengirim "sinyal" melalui WebSocket ke semua browser yang mendengarkan.
4 React menangkap sinyal itu dan memperbarui tampilan UI secara otomatis — tanpa reload, tanpa polling manual setiap beberapa detik.
5 Saat komponen React dihancurkan (user pindah halaman), koneksi WebSocket harus ditutup agar tidak terjadi kebocoran memori.
💡 Insight Utama

Realtime adalah salah satu fitur paling "wow" untuk ditunjukkan ke klien atau penguji skripsi. Bayangkan membuka dua tab browser secara bersamaan — menambahkan data di tab A, dan tab B langsung menampilkannya tanpa refresh. Efek ini terlihat seperti sihir, padahal hanya perlu beberapa baris kode dengan Supabase!

Uji, Rilis & Proyek Akhir 120 menit Modul Praktikum Terpisah

⚡ Modul Mandiri Pertemuan 15
Materi Lengkap Tersedia di Halaman Khusus:
▲ Buka Panduan Deploy Vercel (P15)
🏠 vs 🌐 Localhost vs Cloud Hosting

localhost:5173 ibarat toko di dalam garasi rumah — hanya Anda yang bisa melihatnya. Vercel menyalin kode ke server internet publik (CDN global) sehingga siapapun di seluruh dunia bisa mengaksesnya via URL *.vercel.app.

⚡ Pipa Otomasi CI/CD Modern

Tidak perlu upload file manual via FTP! Cukup jalankan git push ke GitHub, Vercel secara otomatis mendeteksi perubahan, mengompilasi bundel kode, dan menerbitkan pembaruan secara live dalam hitungan detik.

🔐 Brankas Environment Variables

Kunci database (Supabase URL & Anon Key) tidak boleh ditulis langsung di kode publik. Simpan di menu Settings → Environment Variables di Vercel agar koneksi database aman dari pencurian kunci.

Yang dibahas

  • Perbedaan menjalankan di localhost (port lokal) vs server edge hosting publik Vercel
  • Alur 5 Fase Deploy: Siapkan Laptop ➔ GitHub ➔ Vercel ➔ Update Otomatis ➔ Database Supabase
  • Penanganan error deploy: environment variables tidak terbaca, routing SPA 404, dan cara rollback versi
  • Membaca build log di dashboard Vercel secara tenang menggunakan AI Diagnostic prompt

Praktik di kelas

  1. Push seluruh commit repository lokal ke GitHub (git push -u origin main)
  2. Buka Vercel Dashboard, import repository GitHub, dan klik Deploy
  3. Tambahkan VITE_SUPABASE_URL dan VITE_SUPABASE_ANON_KEY di Environment Variables Vercel, lalu Redeploy
  4. Buka link live dari browser smartphone, uji coba transaksi, dan verifikasi data masuk ke Supabase Table Editor
!

Sebelum push ke GitHub, periksa file .gitignore. Pastikan file .env.local yang berisi kunci rahasia tidak ikut terkirim ke repository publik GitHub.

Output pertemuan Tautan URL aplikasi publik (*.vercel.app) yang aktif, terenkripsi SSL/HTTPS, dan berfungsi normal saat diuji dari smartphone.
Kesalahan yang sering terjadi Aplikasi sukses di laptop tetapi layar putih di server publik karena lupa mengisi Environment Variables di dashboard Vercel atau lupa klik Redeploy.
